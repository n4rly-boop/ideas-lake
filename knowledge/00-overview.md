## Задача проекта

Официальная формулировка (слайд 28, «Автономные агенты | Лето с AIRI 2026»), восстановленная дословно по смыслу:

Участники строят **многоуровневое агентное хранилище**, которое автономно извлекает из научных и научно-популярных статей, документации и фрагментов вывода экспериментов **не текстовые выдержки, а обезличенные карточки идей с высокоуровневыми концепциями** в форме:

`концепция → условия применения → эффект → ограничения → связи`

Хранилище **растёт автоматически**, используется агентами для поиска стратегий и переиспользуется для дальнейшей эволюции и генерации агентных пайплайнов.

**Основа, названная в слайде:**

| Что | Ссылка |
|---|---|
| A-MEM | arXiv:2502.12110 |
| HiMem | arXiv:2601.06377 |
| Код | `AIRI-Institute/gigaevo-memory` («prepare memory for CARE implementation») |
| Модели | LLM с function calling для извлечения + embedding-модель для векторного поиска |

**Критерий успеха, названный в слайде:**

1. хранилище со **100+ карточками концепций**;
2. **автоматические связи** между карточками;
3. **дедупликация в рамках одного домена**;
4. **демо**: агент отвечает на запрос релевантными стратегиями **со ссылками на источники**.

**Пример карточки со слайда (verbatim):**

| поле | значение |
|---|---|
| концепция | `cascaded evaluation` |
| условия применения | дорогая оценка кандидатов |
| эффект | −70% compute на отсев |
| ограничения | нужен дешёвый прокси-скор |
| связи | `tiered routing` · `MAP-Elites` |

Читается так: карточка обязана нести **измеримый или хотя бы заявленный эффект с числом**, **предусловие**, при котором приём вообще имеет смысл, **цену применения** и **типизированные связи с соседями**. Ни одна из четырёх изученных систем не выдаёт все пять полей.

### Что это на самом деле

**`IdeaL`.** Это не хранилище карточек и не пайплайн извлечения — это **транспорт и дисциплина линковки**. Его тезис («no algorithm decides how ideas relate — Claude does, by reading the whole store») реализован буквально: весь SQL сосредоточен в `server/db.py`, единственные пути записи ребра принимают `target_id` и `type` **из тела запроса**, никакой эвристики в write-path нет [01] 01-repo-ideal.md:33. Три конкретных приёма: формат «весь store как один markdown с самоописывающей шапкой», обязательный `note` ≤12 слов на каждом ребре с правилом «only link ideas whose relationship you could defend in one sentence», и `IDEAL_ON_UNKNOWN_TARGET=reject` (ссылка на несуществующую карточку откатывает весь запрос — «so you never believe a nonexistent link exists») [01] 01-repo-ideal.md:265-269. Чего в нём нет: ingestion, полей карточки, анонимизации, доменов, версионирования, демо-агента. И известный дефект: `meta` (где живёт провенанс) **не рендерится в markdown-экспорте** — основной read-path теряет источник [01] 01-repo-ideal.md:142-150.

**`gigaevo-memory`.** Это **не «модуль памяти агента»**, а бэкенд-сервис версионируемого хранилища артефактов: ~30k строк Python, 838 тестовых функций, миграции с гейтом round-trip в CI [02] 02-repo-gigaevo-memory.md:12. Слово «memory» здесь означает «persistent store», а не «agent memory»: ни суммаризации, ни извлечения, ни консолидации, ни forgetting, ни графа знаний [02] 02-repo-gigaevo-memory.md:11. Зато готовы: `EmbeddingBackend` (ABC, 3 метода — русскоязычная модель подключается в 20 строк), `SearchStrategy` (ABC), `Reranker` (Protocol + пустой реестр), семантический дедуп с тестами, lineage-BFS, каналы, namespace-изоляция [02] 02-repo-gigaevo-memory.md:274-304. Мины: `ENABLE_VECTOR_SEARCH=false` по умолчанию (векторный поиск и дедуп отдают 503 пока флаг не поднят), `memory_cards` — второсортный тип без `PATCH`/`favourite`/`run-recorded`, вебхуки возвращают 501, а `VECTOR_DIMENSION=384` **фиксируется на этапе миграции** — смена модели эмбеддингов требует новой миграции [02] 02-repo-gigaevo-memory.md:17, 02-repo-gigaevo-memory.md:244, 02-repo-gigaevo-memory.md:48.

**`gigaevo-core/ideas_tracker`.** Это **банк эволюционных «рычагов» (levers) для одного домена — оптимизации кода**, и он честно работает end-to-end: извлечь идею из мутации → классифицировать → дедуплицировать → обогатить → **посчитать измеренный эффект на фитнес** → записать → достать обратно в промпт мутатора [05] 05-repo-gigaevo-core.md:12. Его сильнейшая часть — origin-анализ (IntroGain, квартили, перцентили, MAD-z) и `usage.median_delta_fitness`: эффект здесь не самооценка LLM, а статистика по реальным дельтам фитнеса [05] 05-repo-gigaevo-core.md:1368. Но источник идей ровно один — вывод LLM-мутатора; `grep` по `arxiv|pdf|paper|literature` в memory-подсистеме не даёт ни одного попадания [05] 05-repo-gigaevo-core.md:13. И грамматика описания жёстко привязана к диффу кода: `[UNVERIFIED_]<VERB> <target> [<old>→<new>]: <mechanism>; support=N; Δbest=+F; co=[t1,t2]`, где `VERB ∈ {ADD, REMOVE, UPDATE, SWAP, USE}`, а верификация сверяет рычаг с AST Python — идея из статьи в эту грамматику физически не ложится [05] 05-repo-gigaevo-core.md:1176. Плюс мёртвые ветки: ранжирование `support × Δbest` реализовано, но **не подключено**, а сигналы для него никто не пишет — ключ сортировки всегда `0 * 0 = 0` [05] 05-repo-gigaevo-core.md:978.

**`idea_evolve`.** Это личная работающая реализация участника команды. **Где она сильна:** пятисостояний жизненный цикл идеи с правилом «опровергнутое знание — тоже знание, файл не удаляется» [03] 03-idea-evolve-and-pages.md:67; `coverage_matrix.md`, учитывающий не идеи, а **комбинации** идей с результатами [03] 03-idea-evolve-and-pages.md:239; разделение `idea` / `pattern` / `fact` как трёх эпистемических статусов; и Track A / Track B — принудительный противовес тому, что «the knowledge base … create a gravity well that pulls every agent toward incremental refinement» [03] 03-idea-evolve-and-pages.md:302.

- **README расходится с данными.** Обещает Sidon 66 → 89 за 7 поколений; фактический `history/score_progression.md` даёт 66 → **105**, а верхняя граница в `state_of_affairs.md` — ~109, а не ~100. README устарел и **занижает** результат [03] 03-idea-evolve-and-pages.md:390-420.
- **Гниль знания на живых данных.** В `knowledge/ideas/active/` лежат `fact_001.md`, `fact_002.md`, `pattern_009.md` — записи не того типа не в той директории. `fact_001` существует в двух расходящихся копиях: `confidence: 0.8, verified: false` против `confidence: 1.0, verified: true`. Система сама это заметила и не починила — тело `idea_004.md` заканчивается признанием «the stale copy in ideas/active/ should be deleted» [03] 03-idea-evolve-and-pages.md:421-499.
- **База знаний — на один прогон.** Спецификация V4 предписывает при смене задачи стирать `knowledge/`, `population/`, `history/`, `reports/`, `feedback/`, `briefs/`; единственный кросс-прогонный артефакт — `papers/summaries/` [03] 03-idea-evolve-and-pages.md:678-695. Проект 28 — про **межзадачное** переиспользование. Это не деталь реализации, а расхождение с посылкой.
- **Оркестратор не проверен.** Тестами покрыт только контракт harness-адаптеров (234 строки); логика оркестратора, схемы знания и переходы жизненного цикла не покрыты — что напрямую объясняет гниль. Автор сам перечисляет непроверенное end-to-end: разрешение путей родителей при кроссовере, конвейер experimentator → knowledge, обновление кластеров ревьюером, поток запросов на эксперименты, бутстрап кластеров, авто-одобрение `--allowedTools` [03] 03-idea-evolve-and-pages.md:517-549.
- **Спецификация разошлась с живым конфигом**: таймауты 2700 вместо 900, `max_turns.explore` 1500 вместо 80, ревью консистентности каждое поколение вместо каждого третьего, harness по умолчанию `opencode`/`zai/glm-5.1`, а не Claude Code [03] 03-idea-evolve-and-pages.md:500-516.

## Научная база

### A-MEM (arXiv:2502.12110, NeurIPS 2025)

Схема заметки (уравнение 1): `m_i = { c_i, t_i, K_i, G_i, X_i, e_i, L_i }` — content, timestamp, keywords, tags, context, embedding, links [04] 04-papers.md:64-76.

| Приём | Формула / место |
|---|---|
| **Один LLM-вызов на извлечение семантики** | eq.2: `K_i, G_i, X_i ← LLM(c_i ‖ t_i ‖ P_s1)`, JSON-схема в Приложении B.1 |
| **Эмбеддинг по конкатенации всех текстовых полей** | eq.3: `e_i = f_enc[concat(c_i, K_i, G_i, X_i)]` |
| **Линковка = cosine-префильтр + LLM-арбитр** | eq.4–6, `k = 10` по умолчанию; плато на `k = 10` у обеих статей |
| **`evolution_history`, `retrieval_count`, `last_accessed`, `evo_threshold=100`** | есть в коде `A-mem-sys`, **нет в статье** [04] 04-papers.md:103-111, 04-papers.md:164 |

**Известные ограничения A-MEM:**

- **Нетипизированные рёбра.** `L_i` — плоское множество id, без типов и весов; «противоречит / уточняет / является частным случаем» в A-MEM нет [04] 04-papers.md:135.
- **Memory Evolution как перезапись соседей.** eq.7 замещает `m_j` на `m_j*` без версионирования.
- **`merge` / `prune`.** Объявлены в JSON-схеме `P_s3`, **не реализованы в пайплайне** — расхождение есть и в статье, и в коде [04] 04-papers.md:162.
- **Цена записи.** `O(k)` LLM-вызовов на каждую новую заметку (эволюционируется каждый из k соседей). При `k=50` это дорого; на корпусе из тысяч статей — другой порядок стоимости [04] 04-papers.md:245.
- Adversarial — единственная категория, где A-MEM проигрывает голому LoCoMo (50.03 против 69.23). **На распознавании «ответа нет» память вредит** [04] 04-papers.md:249.

Ориентиры по стоимости: ~**1 200 токенов на memory-операцию** (85–93 % экономии против 16 900 у baseline), <$0.0003 за операцию; ретрив 0.31 µs → 3.70 µs при росте 1K → 1M заметок, память `O(N)`, 1.46 GB на 1M [04] 04-papers.md:210-221.

### HiMem (arXiv:2601.06377)

| Приём | Почему |
|---|---|
| **Иерархия «источник → карточка» с иммутабельным нижним слоем** | Ablation: убрать Episode Memory — минус 11.42 GPT-Score; убрать Note Memory — минус 1.08. **Сырой контекст критичен**, слой абстракций даёт скорость и «semantic anchors», а не точность [04] 04-papers.md:506 |
| **Трёхстадийное извлечение с неразрушающим контрактом** [04] 04-papers.md:382-387 | Note Memory без KA: 57.51 → 63.44 GPT-Score |
| **Избирательная нормализация** | KA для Episode Memory **ухудшил** результат (79.63 → 78.12): «semantic alignment should be memory-type aware» [04] 04-papers.md:519 |
| **Конъюнктивный триггер реконсолидации** | Авторы сами признают: устаревшее знание, которое не всплывает в запросах, не чинится **никогда** [04] 04-papers.md:559 |
| **Дешёвый точный дедуп через `hash`** | md5 по нормализованному `concept` отсекает точные дубли до всяких LLM-вызовов [04] 04-papers.md:637 |
| **`contradictory → DELETE`** | Би-темпоральная инвалидация из Zep/Graphiti: у ребра есть `t_valid`/`t_invalid`, противоречащее ребро инвалидирует старое, **ничего не разрушается** [04] 04-papers.md:571 |
| **Dual-Channel Segmentation** | Заточена под диалог (topic shift + emotional surprise) [04] 04-papers.md:637 |
| **best-effort как дефолт** | Оказался **медленнее** hybrid (1.82 против 1.53 с), хотя экономнее по токенам (1 134 против 1 272) [04] 04-papers.md:637 |

**Флаги достоверности HiMem:**

1. По **F1** HiMem **проигрывает Mem0 во всех категориях** и в overall (34.95 против 48.16), при том что по GPT-Score выигрывает (80.71 против 68.74). Расхождение в 13+ пунктов в пользу разных систем — «это ровно тот случай, когда метрика выбирает победителя» [04] 04-papers.md:494.
2. **Судья и бэкенд — одна и та же модель GPT-4o-mini** [04] 04-papers.md:471.
3. §3.3 описывает A-MEM **неверно** — как систему с «entities, relations, and temporal features»; это описание Zep/Graphiti, а не A-MEM [04] 04-papers.md:565.
4. A-MEM и SeCom процитированы в §3.2 как «работы, изучающие LLM-as-a-Judge и его смещения» — ни та, ни другая ими не является [04] 04-papers.md:566.
5. Выигрыш от эволюции памяти честно маленький: **+5.85 % на Note Memory, ~0.28 % на overall** [04] 04-papers.md:529.

### Ближайший prior art

Три работы 2026 года занимаются **идеями, а не диалогами**, и все три подтверждены на arXiv [04] 04-papers.md:637-750:

| Работа | Что сделали |
|---|---|
| **ResearchStudio-Idea** (arXiv:2607.04439, июль 2026) | Прошли **1 947 статей ICLR / ICML / NeurIPS 2021–2025**, вывели 31 повторяющийся ideation sub-pattern → **15 переиспользуемых паттернов в виде структурированных карточек**. Навыки: Paper-Search, **Scoop-Check** (проверка, что идею уже заняли), IdeaSpark |
| **AutoSci** (arXiv:2605.31468) | `SciMem` = **Long-Term Knowledge Memory** (переиспользуемое знание) + **Active Research Memory** (артефакты проекта). `SciEvolve` превращает фидбэк в **версионированные** обновления памяти |
| **DeepInnovator** (arXiv:2602.18920) | Автоматический пайплайн извлекает структурированное знание из неразмеченной литературы; парадигма «Next Idea Prediction» тренирует 14B-модель. Win rates 80.53–93.81 % |

### Чего в изученной литературе нет

1. **Анонимизация** — ни одна статья не обсуждает отвязку идеи от источника, автора, проекта, датасета [04] 04-papers.md:751.
2. У A-MEM поля описательные, у HiMem категориальные, причинно-условных нет ни у кого [04] 04-papers.md:751.
3. Логи экспериментов — это в основном то, что **не** сработало; обе статьи извлекают только утверждения о том, что есть [04] 04-papers.md:751.
4. У A-MEM `merge` не реализован, у HiMem Stage 3 слияние прямо **запрещает**, а `Equivalent → NONE` просто выбрасывает дубль. Алгоритма «две карточки описывают одну идею — слить, сохранив оба источника и оба набора условий» нет ни у кого [04] 04-papers.md:751.
