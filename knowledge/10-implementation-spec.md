Проект, объявивший fail-open запрещённым, обязан ловить их ассертами, а не глазами: отсюда восемь новых пунктов в §6.

Против `06` §3.3 и сэмпла Даши: `concept` → `text` (симметрия с листом: у обеих нод `text` и его `vector`); `target_score` → `trust_score` (в ответе `/retrieve` рядом стоит `score` — ранг выдачи, это разные числа); добавлены `failure_modes` и `differentiation`; `vector_applicability` (`06:183`) в MVP не заводится — помечено «под абляцию», второй векторный канал дороже, чем даёт до первых замеров.

**Граница `limitations` / `failure_modes`** идёт в промпт пере-вывода дословно, иначе LLM положит одно и то же в оба поля:
- `limitations` — условие входа: «требует предварительно обученного и замороженного энкодера»;
- `failure_modes` — режим отказа: «слишком слабый энкодер → потеря семантики».

**Инварианты:** `id` стабилен при пере-выводе; `effect_claimed` и `effect_observed` **никогда не сливаются** (`06:200`); листья только пополняются или переназначаются.

### 1.4 Кто что пишет

| Пишет | Поля |
|---|---|
| **A** (я) | весь `Source`, весь `Thesis`, у `Idea` — `id`, `text`, `applicability_conditions`, `limitations`, `failure_modes`, оба агрегата эффекта, `vector`, `rederived_at_leaf_count`, позже `differentiation` |

`id` новой идеи генерирую я в момент решения «new»: решение и запись обе на мне, а в одном батче второй тезис может линковаться к идее, созданной первым, — ждать ответа хранилища негде. `uuid7()` появился только в Python 3.14, у нас 3.12 (`09:293`), поэтому `uuid4`.

## 3. Общие механизмы

### 3.1 `llm.py`

```python
QWEN_9B  = ("http://82.202.157.243:8080", os.environ["LAKE_KEY_9B"])
QWEN_35B = ("http://82.202.156.206:8080", os.environ["LAKE_KEY_35B"])

class LLMError(RuntimeError): ...

def complete(prompt: str, *, system: str, schema: dict, op: str,
             max_tokens: int, timeout: float, model=QWEN_9B,
             temperature: float = 0.0) -> dict:
    """One schema-forced call. Returns the parsed object. Raises on any deviation."""

def assert_grammar_works(model) -> None:
    """Canary. Raises if the server silently ignores the schema."""
```

Тело `complete`:

1. payload — вложенная форма, единственная рабочая: `response_format = {"type": "json_schema", "json_schema": {"name": op, "schema": schema}}` (`probe-results.md:10`). Плоская форма из README llama.cpp отдаёт HTTP 200 и прозу (`probe-results.md:11`);
2. `chat_template_kwargs = {"enable_thinking": false}` — всегда (`probe-results.md:34`);
3. `temperature=0` на извлечении (требование `CLAUDE.md`);
4. **`timeout` обязателен и без дефолта** — вызывающий обязан его назвать (§8). Замеры: 9B на ~400 выходных токенов — 7.0 с, 27B с thinking — до 59 с (`probe-results.md:25,27`). Без таймаута зависший сокет вешает 25-минутную фазу линковки и `/retrieve` с бюджетом p95 ≤ 5 с; очередь `pending_link` зависание не ловит, потому что исключения не происходит;
5. **`finish_reason != "stop"` → `LLMError` до `json.loads`** (`probe-results.md:33`);
6. `json.loads(content)`; исключение → `LLMError`. Ретраев на `JSONDecodeError` нет — этот класс ошибок закрыт грамматикой, а не повторами (`08:153`, в отличие от `gigaevo-core analyzers.py:186` с десятью ретраями);
7. **проверка усечения по `maxLength`**: обход разобранного объекта, и если длина строкового поля **равна** объявленному в схеме `maxLength` — `LLMError`. См. ниже, это второй fail-open;
8. ретрай только на сетевую ошибку, таймаут и HTTP 5xx: 2 попытки, пауза 2 с. Пустая строка на исключении, как в `gigaevo-core llm.py:156-158`, не возвращается никогда.

**Требования к схемам** (`models.py`): никаких `$ref` — `pydantic.model_json_schema()` генерит их всегда, а llama.cpp резолвит только после PR #21699 и упирается в `MAX_REPETITION_THRESHOLD 2000`, после чего грамматика **молча не собирается** (`09:67`). Поэтому схемы — литеральные плоские `dict` с `additionalProperties: false`.

**`maxLength` — второй fail-open, и он опаснее первого.** Грамматика режет строку посреди слова и **закрывает её легально**: `finish_reason="stop"`, JSON валиден, `json.loads` проходит, наружу уходит `'Population Diversity Maintenance (e.g., '` (`probe-results.md:47`). Проверка `finish_reason` (пункт 5) этот случай не видит — генерация и правда завершилась штатно. Отсюда пункт 7: равенство длины объявленному потолку считается усечением. Ложные срабатывания возможны и приемлемы — потолки ставятся с запасом именно для того, чтобы в них не упираться, а упор в потолок и есть признак разгона.

Схемы и dataclass'ы держатся вместе одним ассертом в `selfcheck` (§6.11), а не аккуратностью: имена свойств схемы обязаны быть подмножеством полей соответствующего dataclass.

**Канарейка** гоняется в начале каждого прогона на каждой используемой модели — ловит разом плоскую форму `response_format`, непогашенный thinking и молчаливый игнор схемы (`probe-results.md:38-43`):

```python
CANARY = {"type": "object", "properties": {"canary": {"const": "llamacpp"}},
          "required": ["canary"], "additionalProperties": False}
```

**Маршрутизация моделей:**

| Шаг | Модель | Почему |
|---|---|---|
| `parse`, `generalize`, `rederive`, `rewrite` | 9B | массовые и механические; 16 слотов, 728 tok/s на 16 параллельных |

`stub_store.py` — тот же интерфейс на SQLite (`08:62`), **временный**: умирает в день переезда на Neo4j.

                    retrieved_at, run_success INT, run_meta TEXT);
CREATE TABLE idea(id TEXT PRIMARY KEY, text, applicability_conditions, limitations,

### 3.5 `index.py` — индекс тезисов, мой навсегда

**Решение §0.1.14: индекс тезисов остаётся у A и на Neo4j не переезжает.** Вопрос «где физически живёт векторный индекс» стоял открытым с 27-го (`06:538`, `07:94`, `08:406` вопрос №4 Даше, ответа нет); `search_theses` попал в C2 не по решению, а потому что `06` §5.3 описал ретрив как «поиск по индексу тезисов», а чей это индекс — оставили на потом. Закрываю в свою сторону. `06:139` вариант «отдельный слой» разрешает прямым текстом, так что это не против командного решения по Neo4j.

```python
def index_theses(theses: list[Thesis]) -> None     # вызывается из фазы 2 рядом с write_theses
def search_theses(query: str, k: int) -> list[dict]  # {thesis_id, idea_id, score, bm25_rank, vec_rank}
def rebuild_from(path: str) -> int                 # переигрывание staging.jsonl, возвращает число тезисов
```

Четыре причины, и первая решающая:

1. **Переезд на Neo4j стоит в плане как «если готов»** (§9, 31 июля). Если поиск живёт у B и B не успевает, у read path в день демо нет дома. Если у меня — просрочка B стоит только `get_ideas` и `neighbors`, а они деградируют мягко: `neighbors` уже возвращает `[]` при пустых рёбрах, `get_ideas` отдаёт stub. Поиск по тезисам — ядро read path (`06:76`), и ставить его за чужой недоделанный сервис на защитной неделе — крупнейший риск расписания в блоке.
2. **Модель эмбеддингов и query-префикс не дублируются.** Они у меня (§3.2), вектора тезисов пишу тоже я (§1.4). У B индекс потребовал бы либо той же модели с тем же префиксом на её стороне, либо вектора в сигнатуре; цена рассинхрона — не исключение, а тихо просевший косинус.
3. **Абляция RRF против min-max — моя целиком**, без правки контракта на защитной неделе. `bm25_rank` и `vec_rank` я и так считаю сам.
4. **Уже написано.** FTS5 + numpy + RRF — `09-raw/hybrid_recipe.py`, 96 строк, self-check зелёный.

```sql
-- отдельный файл data/index.db, переживает смерть stub_store
CREATE TABLE idx_thesis(rowid INTEGER PRIMARY KEY, thesis_id TEXT UNIQUE,
                        idea_id TEXT, text TEXT, vec BLOB);
CREATE VIRTUAL TABLE thesis_fts USING fts5(text, tokenize='porter unicode61');
```

**Отдельный файл, а не таблица в `lake.db`** — потому что `stub_store` документирован как выбрасываемый, а индекс нет; лежали бы вместе — снесли бы вместе в день переезда.

**`thesis_fts` — обычная таблица, не external-content** (правка §0.1.11). Черновик DDL нёс `content='thesis', content_rowid='rowid'`, а это форма, которую SQLite **не синхронизирует сам**: нужны либо три триггера, либо ручная вставка, ни того ни другого в спеке не было. Итог — пустой индекс, `MATCH` без единой строки, BM25-плечо молча в ноль, RRF от одного списка = тот же список, гибрид выродился в чистый косинус, и заметно это только по метрике. Обычная форма дублирует текст (~2000 тезисов × ~200 симв. ≈ 400 КБ) и совпадает с проверенным `09-raw/hybrid_recipe.py:14`.

FTS5 — public domain, идёт в stdlib; на этой машине sqlite 3.51.0, `bm25()` и porter-стемминг работают (`09:115`). Косинус — numpy brute-force, на нашем масштабе ANN-индекс не нужен (`09:119`). **Матрица векторов держится в памяти** и инвалидируется на запись: 2000 × 384 f32 = 3 МБ.

**Индекс — производное, и он может разъехаться с графом.** Цена названа, закрывается двумя вещами: `index_theses` вызывается в той же функции, что и `write_theses` (§4.7, фаза 2), а `rebuild_from("data/staging.jsonl")` пересобирает индекс с нуля за секунды — вектора в staging уже лежат (§4.7). Рассинхрон ловится ассертом `selfcheck` §6.19, а не глазами.

### 4.3 `ingest/parse.py` — шаг 1c

```python
def parse_section(section: Section, abstract: str, limitations: str) -> list[DraftThesis]
```

**Один вызов на секцию**, но в каждый подмешиваются абстракт и секция Limitations как справка. Причина: `draft_limitations` назван главным риском качества (`08:391`), а тезис из Method без Limitations не знает о цене приёма ничего. Цена решения — абстракт передаётся ~6 раз на статью.

Схема выхода (плоская, `additionalProperties: false`, `maxItems: 6`):

```json
{"theses": [{"text": "...", "context": "...", "effect": "...", "locator": "...",
             "draft_text": "...", "draft_applicability": "...", "draft_limitations": "..."}]}
```

Правила промпта — заимствования, каждое с адресом (`08:142-149`):

1. **Приём, а не пересказ.** Тезис описывает переиспользуемый рычаг; иначе получаем 39 % тавтологий, как в собственном аудите GigaEvo (`08:144`).
2. **Число живёт в тезисе.** `effect` копируется, а не пересказывается (`08:145`).
3. **Не выдумывать.** «You MUST treat these facts as the only source of truth» — Stage 2 HiMem (`08:146`).
4. **Разделять, а не сливать.** «You MAY split one note, but you MAY NOT merge multiple input facts» — Stage 3 HiMem (`08:147`).
5. **Атомарность с ограничителем.** «A claim plus the essential rationale that makes it make sense is **one** idea» — IdeaL (`08:148`).
6. Потолок 6 тезисов на секцию, 30 на документ; второй потолок держится кодом (`08:149`).
7. Схема в промпте повторяется словами с типами полей и правилом «Only use properties defined above» — приём TrustGraph `ontology-prompt.md`; это второй фильтр рядом с грамматикой, а не дубль (`09:82`).

`draft_applicability` и `draft_limitations` помечаются `derived: true`: в тексте статьи их чаще всего **нет**, это вывод, и метрика «верность полей» к ним не применяется — подтвердить источником нельзя по определению (`08:151`).

`max_tokens = 2500` — шесть тезисов по ~150 токенов плюс запас.

**JSONL из `09:81` не берём, и это решение, а не пропуск.** TrustGraph выдаёт по объекту на строку ровно затем, чтобы обрыв генерации терял одну строку, а не весь ответ. У нас `response_format.json_schema` принуждает **один** объект — построчную форму им не выразить, а отказ от схемы ради JSONL вернул бы ручной парсинг с ретраями, то есть ровно `gigaevo-core analyzers.py:186`. Обрыв закрывается двумя другими способами: `finish_reason` (§3.1 п.5) и запас в `max_tokens`. Цена названа: упор в потолок теряет всю секцию, а не один тезис из шести.

**Батч-оверлей — не оптимизация, а условие корректности** (правка §0.1.13). Обоснование последовательной линковки — «второй тезис может линковаться к идее, созданной первым» — механикой не выполнялось: тезисы уходят в `write_theses` батчем **после** линковки, а кандидаты набираются по тезисам, поэтому идея, только что созданная тезисом №1, на момент тезиса №2 не имела ни одного листа в индексе и в отбор попасть не могла. Одна статья заводила два дубля под один механизм — ровно то, что каскад должен предотвращать. Оверлей — список `(text_hash, vector, idea_id)` в памяти фазы 2; косинус по нему брутфорсом, размер — сотни элементов.

Ступень `[0]` по той же причине сверяется и с оверлеем: абстракт, повторённый в Method, даёт два одинаковых `text_hash` внутри одного источника, и `UNIQUE(source_id, text_hash)` (§1.2) уронил бы `write_theses` целиком, потеряв статью, а не тезис.

**Кандидаты набираются по тезисам, а не по `Idea.vector`** — правка `08:186`. **Названное ограничение:** у идеи с 20 листьями двадцать шансов попасть в top-30 по тезисам, у идеи с одним листом — один. - системный сдвиг «не сливать»: «NEVER fabricate … or mark distinct entities as duplicates» (`09:154`).

**Fail-open запрещён.** У `gigaevo-core` сбой LLM → действие по умолчанию `add`, дубли молча копятся (`08:198`). У нас сбой арбитра → тезис уходит в `data/pending_link.jsonl` **целиком**, вместе с разобранными полями и списком кандидатов, и не пишется. ### 4.6 `ingest/rederive.py` — пере-вывод идеи

Запускается по накоплению **3** новых листьев у идеи (`09:181`). Трогает ровно шесть полей: `text`, `applicability_conditions`, `limitations`, `failure_modes`, `effect_claimed`, `effect_observed`. Вход — **все** листья идеи с их `context` и `effect`, склеенные с `source.type`.

**Триггер — поле, а не счётчик в памяти** (правка §0.1.19). Условие: `len(leaves) - idea.rederived_at_leaf_count >= 3`; после пере-вывода поле переписывается в `len(leaves)`. Счётчик в памяти прогона работал бы только внутри одного запуска, а корпус идёт в несколько заходов, и листья от прогонов через C4 приезжают отдельно и позже — между заходами счётчик терялся бы, и пере-вывод либо не срабатывал, либо срабатывал не там. Поле пишет A: триггер мой, `dirty` остаётся у B и означает другое — «B заметила смену состава листьев».

`id` сохраняется — рёбра и накопленные веса не рвутся (`08:200`). Флаг `dirty` и пересчёт `trust_score` — на B (`06:184`).

`effect_claimed` и `effect_observed` выводятся **двумя отдельными полями схемы**: инвариант «никогда не сливаются» (`06:200`) держится грамматикой, а не аккуратностью промпта.

`differentiation` в этом проходе не заполняется: для него нужны соседние идеи, то есть уже построенные рёбра. Отдельный проход после того, как B их построит.

### 4.7 `ingest/run.py` — оркестрация: две фазы над корпусом

Правка §0.1.12. Черновик гнал каждый источник насквозь (`fetch → parse → generalize → link → write`); разделено на две фазы с файлом между ними.

```
ФАЗА 1 — параллельно, 8 потоков, ничего не пишет в граф
  84 источника → fetch (пауза 3 с, кэш data/raw/)
               → parse секций → generalize

  ▲ ПРИЁМКА: читаю глазами, считаю утечку конкретики и верность полей,

ФАЗА 2 — последовательно, из staging, курсор рядом
  на источник: write_source

               → write_theses батчем, одной транзакцией с create_idea
               → index_theses тем же батчем, тут же (§3.5, иначе индекс разъедется)
               → rederive идей, у которых len(leaves) - rederived_at_leaf_count >= 3
```

Четыре причины, каждая — реальная цена черновика:

1. **Рестарт.** Фаза 2 — 25 минут последовательных вызовов (§4.5). Падение на середине в черновике стоило бы всего прогона; теперь стоит одной строки курсора.
2. **Правка промпта парсера.** После первых 20 статей промпт почти наверняка меняется. В черновике это перегон **всего**, включая линковку и запись; теперь — перегон только фазы 1, граф при этом даже не открывался.
3. **Приёмка стоит в правильном месте.** План на 29-е требует «50 тезисов прочитаны глазами, верность полей и утечка посчитаны» (§9) — то есть **до** того, как что-либо попало в граф. В черновике первая статья уже была записана к моменту, когда я смотрю на её тезисы.
4. **Оверлей и внутрибатчевый дедуп** (§4.5) существуют естественно: фаза 2 — единственное место, где живёт состояние линковки.

Цена: один файл между фазами и отдельный курсор. Кэш `(section_hash, prompt_hash)` (§4.8) при этом остаётся — он экономит **внутри** фазы 1 при правке промпта, затрагивающей не все секции.

Финальный отчёт: число источников, тезисов, идей; доля идей с ≥2 различными источниками; длина `pending_link`; доля утечек конкретики; **число идей без листьев (обязано быть 0)**; суммарные токены и время из трейсов.

### 4.8 Идемпотентность

- `source_id = sha1(url + version)[:16]`;
- `text_hash = md5(normalize(text))`, уникальность по паре `(source_id, text_hash)`;
- повторная подача того же документа → все хеши совпали → ноль записей, ноль LLM-вызовов;
- та же формулировка из **другого** источника → новый лист, и это правильно: именно так копится доверие (`06:189`).

Что **не** закрывается и на что не претендую: v2 статьи с изменённым текстом обработается как новый источник, отозванная статья не откатывается (`08:210`).

Кэш секций ключуется парой `(section_hash, prompt_hash)`: правка промпта парсера обесценивает извлечение, но не перекачивает статьи.

### 5.1 `retrieve/rewrite.py`

Один LLM-вызов внутри `/retrieve`, 9B, флаг `rewrite=true` по умолчанию. Искать надо по решению, а не по задаче (`08:218`); паттерн — MemoRAG: сначала черновая догадка, ретрив по догадке (`08:220`). Кэш по хешу запроса, стоимость логируется отдельной строкой трейса, чтобы D видел её как накладную.

`max_tokens = 200`, `timeout = 20 с` (§8) — при бюджете `/retrieve` в 5 с таймаут здесь не «на всякий случай», а потолок деградации: истёк → идём дальше по сырому запросу, а не падаем. Это единственное место на чтении, где отказ LLM **не** фатален: переписывание — улучшение, а не условие корректности, и §9 ставит его первым в порядке урезания. Факт деградации пишется в лог полем `rewrite_failed`, иначе абляция «помогает ли переписывание» посчитается по загрязнённой выборке.

Число, за которым слежу: одиночный вызов извлечения на ~400 выходных токенов занял 7.0 с (`probe-results.md:25`). Бюджет `/retrieve` — p95 ≤ 5 с (`08:328`), то есть переписывание обязано отдавать короткий ответ. Если не уложится — `rewrite` первым уходит в порядок урезания (`08:376`).

### 5.2 `retrieve/search.py`

Вход поиска — **индекс тезисов**, не идей (`06:138`, `08:225`). Гибрид: BM25 через FTS5 + косинус через numpy, слияние **RRF `k=60`**. Рецепт готов и self-check проходит: `09-raw/hybrid_recipe.py`, 96 строк.

Забираем top-50 тезисов (`08:230`). Индекс — `index.py` (§3.5), мой: вопрос «где он живёт при Neo4j» (`06:538`, `07:94`) закрыт решением §0.1.14, а не оставлен B.

**Запрос обязан проходить через `fts_escape()` перед `MATCH`** — две разные проблемы, обе молчаливые, обе проверены прогоном `09-raw/hybrid_recipe.py`:

1. **Грамматика.** У FTS5 своя: `:`, `-`, `"`, `*`, `OR`, `NEAR`, `^` в сырой строке дают либо `OperationalError: fts5: syntax error`, либо другой смысл. Переписанный 9B запрос вида `cheap proxy: pre-filter candidates` кладёт `/retrieve` целиком — отказ на **чтении**, где ловить его некому.
2. **Неявный AND — и это хуже.** Токены через пробел FTS5 соединяет конъюнкцией. Запрос после переписывания — 8–15 слов; документ, содержащий **все** из них, не существует. BM25-плечо возвращает пустое, RRF от одного списка = чистый косинус, гибрид выродился — **без ошибки, без записи в лог, без изменения формы ответа**. Ровно тот же наблюдаемый эффект, что от ненаполненного FTS-индекса (§0.1.11), и та же нулевая заметность.

Обе закрываются одной строкой: каждый токен в кавычках, соединение через `OR` — `" OR ".join(f'"{t}"' for t in re.findall(r"\w+", q))`. Ранжирование остаётся за `bm25()`, поэтому recall растёт, а верх списка не портится. Пустой результат экранирования (запрос из одной пунктуации) → BM25-плечо пустое, косинус отвечает один; это единственный штатный случай одноплечего поиска.
