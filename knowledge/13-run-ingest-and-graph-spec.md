# 13 — Приём прогонов эволюции, `dirty` и `trust_score` (спека реализации)

Две фичи одной спекой, потому что вторая без первой не имеет данных, а первая без второй
не имеет эффекта:

1. **Приём логов эволюции** — лог мутанта GigaEvo → тезисы формата `run` под идеями озера
   (контракт C4, `07:130-147`).
2. **`dirty` и `trust_score`** — то, что до 2026-07-31 числилось за блоком B
   (`07:16`, `10:136`) и перешло к A.

**Область:** запись в хранилище и чтение из него. **Не входит:** **рёбра между идеями — они
остаются за блоком B целиком** (создание, вес, подкрепление, затухание); модель
трудоёмкости (D); правка кода GigaEvo.

## 1. Что реально лежит в логах

Источник фактов — три прогона на диске: `gigaevo-core/outputs/aime_runs_2026-07-30/runs/aime_seed{1,2,3}/results/evolution_full.csv`.

### 1.1 Формат уже структурирован

(`gigaevo/llm/agents/mutation.py:55-86`), он лежит в колонке `metadata_mutation_output`

Имена полей заморожены на их стороне (`tools/mutation_prompt_sota_final_ensemble.py:220`),
то есть конвертер можно писать на них, а не на догадках.

`description` по их же схеме — «generalizable description … prefer general pattern +

why the same idea could transfer to future mutations» (`mutation.py:46-51`). Это ровно
определение тезиса из `10:§1.2`: формулировка приёма плюс основание. Переизобретать шаг
извлечения не надо.

### 1.3 Ловушки, которые обязана знать реализация

**`-1000.0` — это не фитнес, а маркер отказа валидации.** 111 строк из 308. Причина —
таймаут валидации 2400 с (`README.md:37-52`). Число попадает в ту же колонку, что
настоящие 0.40–0.75. Взять его как значение — значит увести любую формулу доверия и веса
в минус тысячу на одном мутанте. Конвертер обязан трактовать `-1000.0` как «измерения нет»
(`run_success = null`, в `effect` листа числа нет), а не как плохой результат. То же число
поедет к B на вес ребра — поэтому оно не должно доехать туда сырым.

**«Измерения нет» — три разных случая, не один.** Кроме `-1000` (111 строк) есть **пустой
`metric_fitness`** (12 строк, в основном `state=running` — прогон оборвался на них) и
**корень без родителя** (3 строки: фитнес есть, дельты нет). Все три дают `run_success =
None`, но по разным причинам, и в отчёте они считаются **порознь**: слитые в одно число,
они прячут оборванный прогон за отказами валидации.

**Родительского фитнеса в CSV нет.** Есть `parent_ids` — JSON-список `program_id`
(`'["ed2e6c4a-…"]'`), и дельта считается join'ом внутри того же файла. Правила:
корень (`parent_ids == []`) → `delta = None`; родитель с `-1000` или пустым фитнесом →
`delta = None` (в этих трёх файлах таких нет: 0 из 308, но правило нужно раньше данных);
несколько родителей (кроссовер) — берём **максимум** родительского фитнеса, потому что
«стало лучше» имеет смысл только против лучшего из того, из чего сделали. В этих данных
`lineage_num_parents` везде 1, то есть ветка не проверена данными и помечена как таковая.

**`metadata_mutation_output` бывает пустым** — 3 строки из 308. Пустая или неразбираемая
строка **пропускается с причиной и попадает в счётчик** `rows_unparsed`, а не молча.

**`insights_used` — не идентификаторы наших идей.** Это строки собственной памяти GigaEvo,
рендер `[type][tag][severity] — текст` (`gigaevo/evolution/mutation/context.py:100-108`,
модель `gigaevo/llm/agents/insights.py:19-84`). Среди 998 различных строк встречается
служебный мусор вида `invalid_streak: 6` (15 вхождений). Контракт C4 (`07:136-137`)
предполагает, что C пришлёт `used_idea_ids` — **их не существует**. Связь «прогон → идея
озера» устанавливается нашей линковкой, а не доверием к полю. Это правка контракта, §11.

**Смещение выборки названо самими прогонами.** 83–86 % мутантов отброшены по таймауту, и
таймаут убил все трёхшаговые цепочки (`README.md:46-52`). Тезисы, извлечённые отсюда,
описывают то, что успело досчитаться. В `run_meta` кладём `state` и `fitness` как есть,
чтобы это было видно на листе, а не терялось.

## 2. Фича 1 — приём прогонов

### 2.1 Что такое «один прогон» в терминах `Source`

Контракт (`07:142`, `06:186-188`): один `Source` с `type=run`, `version=run_id`,
`run_success` и `run_meta`; обоснование — «один прогон даёт **один** исход и **несколько**
тезисов».

В данных единица с одним исходом — **мутант**, а не запуск seed: у запуска 103 программы и
103 разных фитнеса. Поэтому:

```
Source(type="run",
       url     = f"gigaevo://{run}/{program_id}",     # адрес строки, не сеть
       title   = f"{archetype} · {run}/{program_id}", # БЕЗ фитнеса, см. ниже
       version = program_id,                          # уникален внутри запуска
       run_success = None | True | False,
       run_meta = {run, seed, program_id, parent_ids, generation, iteration,
                   state, fitness, fitness_delta, archetype, justification,
                   insights_used, mutation_model, task})
```

Семантика контракта не меняется — меняется только то, что подставляется в `version`.
`run_meta` не типизирован намеренно (`10:78`), поэтому лишние поля туда класть можно.

**Фитнес в `title` не идёт** (правка ревью): `write_source` — это `INSERT OR REPLACE`
(`stub_store.py:79-86`), перезаливка того же прогона переписала бы строку источника, и
«тот же мутант» выглядел бы изменившимся; а через `POST /sources` смена `title` — это
`409` (`lake/README.md:245`). Фитнес живёт в `run_meta`, где ему и место.

`run_success`:

```
fitness пуст              -> None      # измерения не было (12 строк, §1.3)
fitness == -1000.0        -> None      # валидация отказала (111 строк, §1.3)
parent_ids == []          -> None      # корень, сравнивать не с чем (3 строки)
фитнес родителя пуст/-1000-> None      # база сравнения недостоверна
delta > 0                 -> True
delta == 0                -> False     # 20 строк: «не хуже» — это не «лучше»
иначе                     -> False
```

Отрицательный исход не выбрасывается — он и есть источник контраста (`06:225`, `07:142`).
100 отрицательных дельт против 62 положительных (и 20 нулевых): контраста в этих данных
больше, чем подтверждений, и это надо предъявлять как факт, а не сглаживать.

### 2.2 Тезис из `changes[i]`

```
text     = changes[i].description
context  = f"{archetype} · {task} · {mutation_model}"      # чем и над чем
effect   = f"fitness {parent_fitness} -> {fitness} ({delta:+.2f})" | "измерения нет"
locator  = f"{run}:{program_id}#changes[{i}]"              # обратный адрес в CSV
```

`locator` обязателен и должен быть обратимым: без него лист формата `run` неотличим от
выдумки, а провенанс — критерий 4 ТЗ (`11-vault-export-spec.md:13`).

`justification` и `insights_used` на лист не идут — они про мутанта целиком, а не про одну
правку; их место в `run_meta` источника, по той же логике, по которой исход живёт на
источнике (`06:188`).

### 2.2.1 Одного `changes[i]` для строки staging мало

**[ревизия 2026-07-31, ревью]** Строка staging — это не тезис, а пятёрка
(`run.py:110-124`): `source`, `thesis`, `draft` (`draft_text`, `draft_applicability`,
`draft_limitations`), `idea_fields` и `vector`. Фаза 2 читает **все пять**: `idea_fields`
идут в `Idea` при создании новой (`link.py`), а `_report` пересчитывает утечку через
`generalize.leakage(_draft_of(row), IdeaFields(**row["idea_fields"]))` (`run.py:432-433`)
— строка без `draft`/`idea_fields` уронит отчёт фазы 2, а не «просто не даст полей».

Значит конвертер обязан пройти те же два шага, что и статья:

```
changes[i] --(9B, generalize)--> draft_* + idea_fields --(embed)--> vector --> строка staging
```

`generalize` берётся как есть (`ingest/generalize.py`), эмбеддинг — `embed_docs` по
`thesis.text`, как в фазе 1 (`run.py:105-107`): вектор считается **до** обобщения, потому
что кандидаты набираются тезис-к-тезису.

**Обезличивание для логов — свой список запретов.** `generalize.leakage()` заточен под
статью: он ищет в обобщении число из `effect` и имена датасетов/моделей из `context`. В
логе конкретика другая — `program_id`, имена функций и классов из `code`, `aime`,
`MultiModelRouter`, номера итераций. Промпт обобщения и проверка утечки для `run` дополняются
этим списком; без этого автопроверка будет зелёной ровно там, где утечка есть. Промпт —
отдельным файлом `prompts/generalize/run.txt`, а не веткой `if` внутри одного текста.

> **[реализация 2026-07-31]** Список запретов для лога — не отдельная ветка внутри
> `leakage()`, а третий параметр: `generalize.leakage(draft, out, extra_terms=())`
> (`lake/ingest/generalize.py:52-78`) проверяет `extra_terms` третьим правилом наравне с
> числом из `effect` и именами из `context`. Термины считает `runlog.leak_terms(source)`
> (`lake/ingest/runlog.py:166-179`): `program_id`, `run`, `task`, `mutation_model` и
> `mutant_code_names` (регэксп по `def`/`class` и по вызовам, `runlog.py:120-145`, ловит и
> имя, которое мутант только вызывает, не только то, что определяет) — всё это уже лежит
> в `run_meta` источника, а не только в памяти конвертера, поэтому пересчитывается из
> одной строки staging спустя долгое время после того, как исходный payload с `code`
> исчез. Ровно это и нужно `_report`: он пересчитывает утечку заново для отчёта фазы 2,
> отдельно от того, что насчитал конвертер при заливке, и берёт `runlog.leak_terms` для
> строк с `type == "run"`, пустой кортеж — для остальных (`lake/ingest/run.py:460-464`).

### 2.3 Линковка — переиспользуется целиком

Новый агент линковки не пишем: `lake/ingest/link.py:46-109` уже делает ровно то, что
описано в `12-decisions-meetings.md:121` — кандидаты по индексу тезисов, арбитр 35B, `link` к существующей идее
либо `new`, и «если подошло нескольким — выбирается одна» (`LINK_SCHEMA` отдаёт один
индекс). Fail-closed там же: отказ арбитра → `pending_link.jsonl`, тезис не пишется
(`link.py:21-25`).

Отсюда порядок: конвертер отдаёт **строки того же формата, что фаза 1**, и всё остальное
делает существующая фаза 2 (`lake/ingest/run.py:228-303`) под писательским локом
(`run.py:154-176`). Последовательность линковки — не деталь, а условие корректности
(`link.py:40-43`): два параллельных линкера открывают две идеи под один механизм.

Идемпотентность бесплатна: `text_hash` внутри источника (`link.py:69-70`) и
`UNIQUE(source_id, text_hash)` (`lake/stub_store.py:36`). Повторная заливка того же мутанта
даёт `skipped`, а не дубли.

**Свой staging-файл и свой курсор — обязательны.** Общий `data/staging.jsonl` не годится по
той же причине, по которой его не берёт `/fetch`: фаза 1 сносит корпусный курсор
(`run.py:56-60`), и следующая фаза 2 залила бы в граф все источники, которые ещё ждут
приёмки глазами (`run.py:307-320`). Заливка логов идёт по `data/run/{job_id}.jsonl`.

### 2.4 Стоимость и порядок заливки

**[ревизия 2026-07-31, ревью]** Стоимость вдвое больше, чем стояло в первой редакции: на
каждый `changes[i]` приходится **вызов 9B на обобщение** (§2.2.1) плюс **до одного вызова
35B на арбитраж**. Считать надо от 647 элементов у 182 мутантов с вычислимой дельтой, а не
от 1118 по всем строкам:

- **647 вызовов 9B + до 647 вызовов 35B**, а не «1118 арбитражных»;
- шаг [0] линковки снимает часть арбитражей бесплатно (повторный `text_hash` внутри
  источника), но между разными мутантами тексты разные — рассчитывать на это нельзя;
- заливаем **только мутантов с вычислимой дельтой** (182 из 308): у остальных нет ни
  исхода, ни контраста — 111 отказов валидации, 12 без измерения, 3 корня;
- порядок — по убыванию `|delta|`: информативные первыми, обрыв на любом месте оставляет
  осмысленный срез;
- `limit` есть у ручки и у CLI, и он **логируется в отчёте**; там же — все четыре отсева
  (`-1000`, пустой фитнес, корень, `min_abs_delta`) отдельными числами. Усечение, о котором
  не сказано, читается как «залито всё».

### 2.5 Точки входа

Паритет «модуль == HTTP» обязателен (`11-vault-export-spec.md:114`).

```python
lake.ingest.runlog.from_csv(path: Path, *, limit: int | None = None,
                            min_abs_delta: float = 0.0) -> int     # строк в staging
lake.ingest.runlog.from_payload(payload: dict) -> int              # push-форма C4
```

> **[реализация 2026-07-31]** Не `-> int`: `from_csv` (`lake/ingest/runlog.py:430-437`) и
> `from_payload` (`runlog.py:214-227`) возвращают `dict`-отчёт, потому что §9 п.3 и §12
> требуют каждый отсев отдельным числом, а `int` может нести только одно. Ключи отчёта
> (`runlog.py:413-427`): `run_sources`, `run_theses`, `staging_lines`, `leakage`,
> `rows_unparsed`, `mutants_total`, `mutants_converted`, `mutants_no_changes`,
> `dropped_dead`, `dropped_no_fitness`, `dropped_root`, `dropped_parent_unmeasured`,
> `dropped_min_delta`, `limit` (сентинел `-1`, не `None` — счёт должен остаться числом),
> `min_abs_delta`.

```bash
python3 -m lake.ingest.runlog <evolution_full.csv> [--limit N] [--dry-run]
```

```
POST /run   тело: { run_id, task_id?,
                    mutants: [ { program_id, parent_ids: [...], state,
                                 fitness: float|null, parent_fitness: float|null,
                                 mutation_output: {archetype, justification,
                                                   insights_used, changes[]} |
                                 mutation_output_raw: "<json как в CSV>" } ] }
            -> 202 + job_id, как /fetch (routes.py:250)
```

**Ручка нужна и она одна** (решение 2026-07-31: логи приходят в озеро сырыми). Форма
осознанно **батчевая**: единица исхода — мутант (§2.1), но приезжают они пачкой прогона, а
задание на каждого мутанта означало бы 182 задания в очереди с потолком 100 (`LAKE_QUEUE_MAX`)
и 182 круга фазы 2 под одним локом. Одно задание = один прогон.

- **`mutation_output_raw` принимается наравне с разобранным** — «сырой» и означает строку
  JSON, как она лежит в CSV; разбирает её конвертер, а не отправитель. Битая или пустая
  строка не роняет задание: мутант пропускается, счётчик `rows_unparsed` растёт (§1.3).
- **Дедуп задания** — по `run_id` (`dedup_key`), как `/fetch` дедуплицирует по `arxiv_id`:
  повтор того же прогона возвращает существующее задание, а не заводит второе.
- **`parent_fitness` необязателен**: если прислан — берём, если нет — считаем join'ом по
  `parent_ids` внутри батча (§1.3). Прислать батч без родителей законно, тогда часть дельт
  станет `None`, и это будет видно числом в отчёте, а не догадкой.
- **`400` на входе** — до очереди и до трат на LLM: нет `run_id`, пустой `mutants`,
  неизвестное поле (`extra="forbid"`, как в `RetrieveRequest`).
- **Переполнение очереди** → `429` + `Retry-After`, как у `/fetch`.

CLI — тот же конвертер поверх файла: `from_csv` строит тот же payload и зовёт ту же
`from_payload`. Второго HTTP-пути нет. Запись идёт через очередь (`lake/queue.py`,
`kind="run"`, стадии `phase1`→`staged`→`phase2`) и того же единственного писателя
(`lake/writer_lock.py`).

**Мутант без единого `changes[]` не даёт тезисов.** Если таких оказался весь батч —
задание `failed` с причиной, а не `ok` с нулями: это четвёртый способ кончить
неизменившимся озером к трём известным (`lake/README.md:175-181`).

## 3. Фича 2 — `dirty` и `trust_score`

### 3.1 Рёбра — не здесь

Таблица `edge(source_id, target_id, type, note, weight, evidence)` в хранилище есть и пуста
(`stub_store.py:37-38`), `neighbors()` возвращает `[]`, и ранжирование деградирует в плоский
top-k (`stub_store.py:430-433`, `graph_client.py:144`). **Заполняет её блок B** — создание
рёбер, вес, подкрепление и затухание за ним (`07:16`, `06` §6). Со стороны A остаётся ровно
то, что уже есть: батч на один источник приходит одним вызовом, поэтому со-встречаемость
идей внутри источника B выводит из батча и отдельным полем она не передаётся (`07:69`).
Тезисы формата `run` дают B второй путь подкрепления — набор идей одного мутанта плюс его
исход, — но строит рёбра по ним всё равно B.

A читает рёбра через `neighbors()` на дозаполнении выдачи (`via="edge"`) и не пишет их
никогда.

### 3.2 `dirty`

Смысл (`06:330`, `07:70`): состав листьев изменился с момента последнего пере-вывода.
Сейчас в поле пишется `False` и его никто не двигает (`lake/models.py:106`), а триггер
пере-вывода живёт отдельно — по счётчику `rederived_at_leaf_count` с порогом 3
(`run.py:517-527`).

Два независимых определения одного и того же — это ровно та ошибка, за которую в `06:229`
выброшен булев `verified`. Поэтому:

- `dirty = 1` выставляется **в той же транзакции**, что и запись листьев
  (`create_idea_with_theses`, `stub_store.py:147-155`) — иначе флаг врёт при откате;
- `dirty = 0` снимается там же, где двигается `rederived_at_leaf_count`, — в
  `rederive.maybe_rederive`;
- `_rederive_due()` становится `dirty AND (leaves - rederived_at_leaf_count >= 3)`: порог
  остаётся у счётчика, флаг — дешёвый предфильтр. Одно определение, два представления.

Практический выигрыш: лист формата `run` делает идею грязной, пере-вывод обновляет
`effect_observed` (`06:207`), который сегодня пуст у всех идей, — ради этого поля вся
фича 1 и делается.

> **[реализация 2026-07-31]** Три утверждения этого параграфа и §3.3 одновременно не
> выполнимы, как написано: «`dirty` снимается в `maybe_rederive`», «судья запускается
> там же, где снимается `dirty` — при создании идеи и при каждом пере-выводе», и «отказ
> судьи оставляет идею грязной, чтобы следующий проход повторил» — не сочетаются, потому
> что `maybe_rederive` не вызывается при создании идеи, а после пере-вывода счётчик уже
> сдвинут, и `_rederive_due` для этой идеи больше не сработает: обещанного повтора не
> случилось бы. Реализация разводит два места:
> - `dirty` снимается **только** в `graph_client.set_trust` → `stub_store.set_trust`
>   (`lake/stub_store.py:470-480`), одним `UPDATE`, который пишет счёт и снимает флаг
>   разом: `_update_idea(conn, idea_id, {"trust_score": float(score), "dirty": False})`
>   (`stub_store.py:480`);
> - `rederive.maybe_rederive` `dirty` не трогает вовсе, и это явно оговорено в шапке
>   модуля (`lake/ingest/rederive.py:8-12`): «пере-вывод переписывает, что идея ГОВОРИТ,
>   судья решает, чего она СТОИТ, и они отказывают порознь; расчистка флага здесь
>   потратила бы этот повтор впустую»;
> - судья запускается не «при создании и при каждом пере-выводе», а один раз, **в конце
>   фазы 2**, сводом по `graph_client.dirty_ideas()` (`lake/ingest/run.py:298-309`):
>   `due_trust = graph_client.dirty_ideas()`, `trust_report =
>   trust.sweep(due_trust[:TRUST_PER_PASS])`. Это и есть обещанный повтор: идея, оставшаяся
>   грязной после неудачного суждения, попадает в тот же список `dirty_ideas()` на
>   следующем проходе фазы 2, а не по отдельному триггеру;
> - `_rederive_due()` действительно `dirty AND (leaves - rederived_at_leaf_count >=
>   threshold)`, как просит спека (`lake/ingest/run.py:569-585`, условие на `run.py:583`).
>
> Комментарий на самой модели не обновлён вслед за этим решением: `lake/models.py:112-113`
> всё ещё говорит «`dirty` is set in the same transaction as the leaves and cleared where
> `rederived_at_leaf_count` moves» — счётчик его не снимает, снимает только `set_trust`.

### 3.3 `trust_score` — не формула, а судья

Сейчас в коде: `log(1 + число различных источников)`, считается на чтении и не хранится
(`stub_store.py:11-13,112-115`), шкала нормировки — максимум того же по графу
(`stub_store.py:419-427`), в ранге вес 0.15 (`retrieve/rank.py:90`).

**Решение встречи 5 отменяет формулу** (`12-decisions-meetings.md:78-86`, там же §7 п.3):
одно число, выводимое **few-shot оценкой LLM** по идее и всем её листьям, с 5–10
размеченными примерами в промпте; предпосчёт **на узле** при создании и при перерасчёте,
а не в момент выдачи — `O(N)` вместо `O(500·K)`. Разделение на `usefulness` и уверенность
отвергнуто там же: число одно и несёт полезность.

Что из этого следует для кода:

- поле `idea.trust_score` **начинает писаться** (сегодня столбец есть, но подменяется
  вычисленным на чтении — `stub_store.py:284`); `_stub_trust` уходит целиком;
- `trust_scale()` возвращает **фиксированную 1.0**, потому что судья отдаёт уже
  нормированное число. Это заодно снимает ловушку двух копий формулы
  (`stub_store.py:112-115` и `:424-427`), которые, разъехавшись, дают `trust_norm > 1`
  и молча ломают вес 0.15;
- судья — 35B, как и арбитр линковки; промпт файлом `prompts/trust/system.txt`, не строкой
  в коде (правило `CLAUDE.md`).

**Шкала.** Открытый пункт `12-decisions-meetings.md:143` закрываю так: судья отдаёт
**целое 0–10** перечислением (`enum`), код делит на 10. Причина техническая: грамматика
llama.cpp надёжно держит перечисление, а диапазон обычного `number` она не ограничивает —
ответ «12» проехал бы молча и сделал бы `trust_norm > 1` тем же способом, что и разъехавшиеся
формулы.

**Когда считается.** Ровно там же, где снимается `dirty` (§3.2): при создании идеи и при
каждом пере-выводе. Отдельного триггера нет — второй триггер означал бы второе определение
свежести.

> **[реализация 2026-07-31]** Не два триггера (создание идеи, каждый пере-вывод по
> отдельности), а один: конец фазы 2 читает всё, что грязно, разом
> (`graph_client.dirty_ideas()`, `lake/ingest/run.py:304`) и судит сводом — после того как
> сплиты и пере-выводы этого прохода уже переписали, что идеи говорят
> (`run.py:298-303`). «При создании» и «при пере-выводе» не отдельные события в коде, а
> следствие того, что запись листа и пере-вывод поднимают `dirty` (создание —
> `stub_store.create_idea_with_theses`, `stub_store.py:165-182`); момент, когда флаг
> действительно проверяется и снимается, — один, в конце фазы 2, а не «там же и тогда же».

**Fail-closed.** Отказ судьи — это **не** `0.0` и не тихий пропуск: ноль означает «оценили и
не доверяем», а мы не оценили. При отказе значение не пишется, `dirty` **не снимается**
(следующий проход повторит), отказ считается в отчёте отдельным числом `trust_failed`.
Идея без листьев (легальная после `12-decisions-meetings.md:70-72` — гипотеза) судью не
зовёт вовсе: `trust_score = 0.0` по определению «доказательств нет», и это определение,
а не отказ.

Контраст прогонов (`06:224-225`: отрицательный результат понижает, а не выбрасывается)
теперь обеспечивает не арифметика, а вход судьи: листья формата `run` приходят к нему
вместе с `run_success` источника. Поэтому фича 1 — предусловие фичи 2, а не соседняя задача.

**[ревизия 2026-07-31, ревью] Четыре дыры судьи, каждая закрывается здесь.**

1. **Все листья на вход не влезают.** У одной идеи на первом прогоне было 92 листа
   (`lake/README.md:498`), и это ещё до логов. Промпт «идея + все листья» упрётся в
   контекст, а на выходе — `finish_reason != "stop"` и `LLMError` на каждой большой идее,
   то есть судья ляжет ровно там, где он важнее всего. Потолок — **16 листьев** (та же
   константа, что `MAX_LEAVES` у `split`), отбор детерминированный: сначала листья с
   `type=run` и непустым исходом, потом остальные по `created_at`, при равенстве — по `id`.
   Число поданных листьев и общее число листьев идут **оба** в трейс: «оценено по 16 из 40»
   — это другая оценка, чем «по 40», и она не должна выглядеть одинаково.
2. **Эталонных примеров нет** (`12-decisions-meetings.md:143`) — их пишу я по нашим же 26
   идеям, размечаю руками и показываю до боевого прогона. До этого момента судья не
   включается: промпт из пяти выдуманных примеров даёт число, которое ничем не лучше
   `log(1 + источники)`, но выглядит убедительнее.
3. **Проверки, завязанные на старую формулу, придётся переписать в том же коммите**:
   `stub_store.py:503` (`assert abs(trust - log(2)) < 1e-9`), ранговые проверки
   `selfcheck.py:196,237-246,270` (там `scale = trust_scale()` и точные равенства
   `0.15 * trust / scale`). Оставить их «на потом» нельзя: 25/25 покраснеет по своей
   причине, и первым же движением его снимут вместе со стражем.
4. **Трейс обязателен** (C5, `07:149-159`): судья — LLM-операция, и её токены и `wall_ms`
   идут блоку D наравне с арбитром. Канарейка 35B гоняется до первого вызова судьи, как и
   до арбитража, — мёртвая модель не должна обнаруживаться на середине фазы 2.

**Цена.** Один вызов 35B на каждую созданную идею и на каждый пере-вывод. На корпусе из
84 статей это сотни вызовов, на логах — по одному на каждую тронутую идею за проход. Это
не бесплатно, и это причина, по которой судья стоит в фазе 2, а не в выдаче.

> **[реализация 2026-07-31]** Добавлен потолок на проход, которого в этом параграфе нет:
> `LAKE_TRUST_PER_PASS` (по умолчанию 50) — `lake/ingest/run.py:36`
> (`TRUST_PER_PASS = int(os.environ.get("LAKE_TRUST_PER_PASS") or 50)`), применяется на
> `run.py:305` (`trust.sweep(due_trust[:TRUST_PER_PASS])`). Судятся не все грязные идеи
> прохода, а первые `TRUST_PER_PASS` из `dirty_ideas()` (та отдаёт «старейшие первыми»,
> `stub_store.py:445-455`, чтобы усечённый проход всегда доедал то, что начал предыдущий,
> а не пересуживал одну и ту же голову списка). Усечение названо в отчёте, а не спрятано:
> `trust_due` — сколько было грязных всего (`run.py:306`), `trust_deferred` — сколько
> осталось на следующий проход (`run.py:309`, `max(0, len(due_trust) - TRUST_PER_PASS)`).
> `_print_report` печатает `trust_deferred` отдельной строкой, если он не ноль
> (`run.py:498-500`), чтобы усечённый проход не читался законченным.

## 4. Фича 3 — хранилище переезжает на Bolt

Решение 2026-07-31: **`graph_client` начинает говорить с Neo4j напрямую, инстанс —
локальный** (сервис `neo4j:5-community` в `docker-compose.yml:61-82`, `NEO4J_AUTH: none`).
Aura `37b54210` остаётся тем, чем была, — чужой базой блока B с их тестовыми узлами
(`07:79`); односторонняя заливка туда (`lake/neo4j_load.py`) переездом не отменяется и
живёт отдельно, пока B не скажет иначе.

### 4.1 Форма переезда

`graph_client.py` устроен ровно под это: каждая функция — одна строка делегирования в
`stub_store`, и в шапке файла записано, что бранч Neo4j пишется, «когда база появится»
(`lake/graph_client.py:1-19`). Появляется второй бэкенд `lake/neo4j_store.py` с тем же
набором функций; `stub_store` **не удаляется** — на нём держится офлайновый `selfcheck`
(25 пунктов без сети) и весь CI, где Neo4j нет.

Выбор бэкенда — переменной `LAKE_STORE=stub|neo4j`, по умолчанию `stub`. Отказ на старте —
в **обе** стороны: `LAKE_STORE=neo4j` без `NEO4J_URI` и `NEO4J_URI` при `LAKE_STORE=stub`.
Одностороннюю проверку легко написать и легко не заметить, что она односторонняя: прод, где
забыли переменную, тихо пишет в SQLite и выглядит работающим.

**Фолбэка нет и быть не может.** Недоступный Neo4j — это `STORE_ERRORS` и `503`, а не тихий
переход на SQLite: пустое озеро вместо ошибки — тот же fail-open, что и `ideas: []` на
упавшем графе (`10` §5.4). По той же причине **противоречивая конфигурация — отказ на
старте**: `NEO4J_URI` задан, а `LAKE_STORE=stub` — сервер не поднимается; молча писать в
SQLite на проде, где ждут граф, хуже, чем не подняться. Бэкенд называется в стартовом логе
и в `/healthz`.

> **[реализация 2026-07-31]** Отказ — не буквально «`NEO4J_URI` при `LAKE_STORE=stub`»:
> код (`lake/graph_client.py:44-88`) различает, было ли `LAKE_STORE` **явно** названо.
> `os.environ.get("LAKE_STORE")` без второго аргумента даёт `None`, когда переменная вообще
> не упомянута, — и только это отказывает (`graph_client.py:76-84`): «`NEO4J_URI` задан,
> `LAKE_STORE` не назван вовсе» — это и есть забытый флаг, который тихо пишет в SQLite
> рядом с настроенным графом. А «`LAKE_STORE=stub` написано явно рядом с `NEO4J_URI`» —
> не отказ, сервер стартует (проверено в самопроверке модуля,
> `graph_client.py:264-270`, оба направления — `graph_client.py:257-280`). Причина
> различия названа в самом коде (`graph_client.py:56-66`): `.env.local` этого репозитория
> уже несёт `NEO4J_URI` для одностороннего пуша `lake/neo4j_load.py`, и страж, отказывающий
> на самом факте присутствия переменной, отказал бы существующему, документированному
> деплою (`.env.local.example`, `docker-compose.yml`). Буквальная формулировка спеки была
> бы верна, если бы `NEO4J_URI` в проекте не имел легального смысла без графового
> бэкенда; раз имеет, различать «не сказано» и «сказано `stub`» обязательно, а не
> опционально.

### 4.2 Что придётся дописать, а не переименовать

| Место | Почему не механика |
|---|---|
| `STORE_ERRORS` (`graph_client.py:31`) | Сегодня это `sqlite3.Error`. Не добавить сюда `neo4j.exceptions.ServiceUnavailable` и `Neo4jError` — значит в день переезда все графовые ручки тихо съедут с `503` на `500`. Это предсказано комментарием на месте (`graph_client.py:24-30`) |
| `UNIQUE(source_id, text_hash)` (`stub_store.py:36`) | На нём держится идемпотентность повторной заливки (§2.3). Составной uniqueness-constraint в Community не гарантирован, поэтому в Neo4j ключ становится **вычисляемым свойством** `leaf_key = f"{source_id}\|{text_hash}"` с обычным одиночным constraint, а `MERGE` идёт по нему |
| `create_idea_with_theses` | Одна транзакция (`07:65`) — `session.execute_write` с обеими записями внутри; распад на два вызова возвращает идею с нулём листьев |
| `split_idea` | Тоже одна транзакция и единственный легальный `UPDATE` по тезису (`10` §3.4) |
| `counts` / `all_theses` / `ideas_without_leaves` | Обязаны считать **одним и тем же** обходом `(:Idea)-[:HAS_LEAF]->(:Thesis)`, иначе `in_sync` врёт по строкам, которых никто не видит (`lake/README.md:424`) |
| `_row` | Требование «каждое обязательное поле модели присутствует» переезжает вместе с кодом: у Neo4j схемы нет, возразить некому — так 60 тезисов уже уехали без `vector` (`07:78`) |

Цифры и Cypher переиспользуются из `neo4j_load.py`: метки `Source`/`Thesis`/`Idea`, рёбра
`(:Idea)-[:HAS_LEAF]->(:Thesis)` и `(:Source)-[:YIELDS]->(:Thesis)`, constraints на `id`
трёх меток (`07:77`). Новых зависимостей нет: `neo4j` уже обоснован в `CLAUDE.md`.

### 4.3 Что **не** переезжает

**Индекс тезисов остаётся у A в SQLite** (`07:91-101`) — это решение от 2026-07-28, и
переезд хранилища его не отменяет: модель эмбеддингов, query-префикс и RRF живут в блоке A.
Меняется только то, с чем сверяется инвариант «индекс == хранилище» (`6.19`): теперь
`reconcile` читает `all_theses()` из Neo4j, а не из SQLite. Путь починки (`/admin/reindex`)
не меняется ни строкой.

### 4.4 Три вещи, которые переезд ломает молча

**[ревизия 2026-07-31, ревью]**

1. **Блок B строит рёбра не там, где лежит озеро.** Если A пишет в локальный Neo4j, а B
   работает в Aura `37b54210`, то рёбра B строит поверх **дампа** (`neo4j_load`), а не
   поверх живого графа: наши новые идеи туда не приезжают, пока дамп не прогнали, а их
   рёбра к нам не приезжают вообще. Одно из двух, и это решается **до** переезда, не после:
   либо B подключается к нашему инстансу (тогда `NEO4J_URI` у обоих один), либо `neo4j_load`
   в Aura гоняется после каждой фазы 2 и рёбра B живут в базе, которую A читать не будет.
   Молчаливый третий вариант — «оба пишут каждый в своё» — даёт два разных озера с
   одинаковыми `id`, и обнаруживается это на демо.
2. **`writer_lock` перестаёт быть достаточным.** Сегодня это `flock` по файлу
   (`lake/writer_lock.py`), и он связывает процессы **на одной машине**. База по сети
   доступна и с других: второй писатель с ноутбука соседа замка не увидит и заведёт вторую
   идею под тот же механизм — ровно то, ради чего лок и существует (`lake/README.md:151-157`).
   Пока всё крутится на одном хосте, это годится; ограничение названо здесь, чтобы не быть
   обнаруженным как «странные дубли».
3. **Перенос существующих 88 узлов.** 2 источника, 26 идей, 60 тезисов уже лежат в

   `counts()` до и после, 26/26 идей и 60/60 тезисов с вектором длины 384.

## 5. Идея без листьев: инвариант снят, но не в пустоту

Гипотеза — это идея с `trust_score = 0` и без доказательств
(`12-decisions-meetings.md:70-72`), значит проверка «идей без листьев обязано быть 0»
(`selfcheck.py:292,738,875`) на ней краснеет. Снимаем — **но заменяем, а не удаляем**:
голая проверка ловила настоящую поломку записи (отказ между `create_idea` и
`write_theses`), и без замены она перестаёт ловить что-либо.

**[ревизия 2026-07-31, ревью] Первая формулировка была непроверяемой.** Она требовала у
идеи без листьев «synthesis-источник в своей истории» — но источник у идеи виден **только
через листья** (`get_ideas` склеивает `source` с листа, `07:105`), и у идеи без листьев его
негде взять. Проверка, которая не может прочитать то, что проверяет, — это не страж.

Признак живёт **на самой идее**, отдельным полем:

```
Idea.origin: "extracted" | "synthesized"      # default "extracted", правка C1

было:  ideas_without_leaves() == []
стало: идея без листьев обязана иметь origin == "synthesized" и trust_score == 0.0;
       идея без листьев с origin == "extracted" — поломка записи, как и раньше
```

Поле нужно и само по себе: без него «эту идею вывели из статей» и «эту идею придумала
модель из двух других» — одно и то же состояние базы, и в выдаче их не различить ничем,
кроме косвенных признаков. Один enum, пишет A при создании, B ставит `synthesized` на
своих гипотезах.

На практике счётчик всё равно останется нулём: гипотеза приезжает **с одним синтетическим
листом** (§6), потому что иначе её нечем найти. Голая идея без листа означает ровно то, что
означала раньше, — оборванную транзакцию.

## 6. Гипотеза в выдаче: синтетический лист, вперемешку с идеями

Решение: гипотезы отдаются **вперемешку с идеями**, отдельного канала нет
(`12-decisions-meetings.md:141`). Механика — синтетический лист:

```
Source(type="synthesis", url=f"lake://synthesis/{idea_id}", version=<ts>,
       title="синтез: <родители>")
Thesis(text    = текст гипотезы + спекулятивная применимость,
       context = "синтез из <id родителей>",
       effect  = "не проверено",
       locator = f"synthesis/{parent_ids}")     # обратный адрес к родителям
```

Три следствия, и все три бесплатны:

1. **Ищется тем же гибридом.** Лист попадает в индекс тезисов обычным `index_theses`,
   поэтому гипотеза находится тем же BM25+косинусом и приходит в ту же выдачу — никакого
   второго пути поиска и никакой правки контракта C3.
2. **Дедуп гипотез получается сам.** Синтетический лист проходит ту же линковку
   (`link.py:46-109`): арбитр либо прицепит его к существующей идее — и повторный синтез
   того же не заведёт второго узла, — либо скажет «новая». Открытый пункт
   `12-decisions-meetings.md:146` этим закрывается.
3. **Провенанс не врёт.** `type="synthesis"` и `url=lake://synthesis/...` говорят, что
   утверждение не из статьи и не из прогона. Правило «нет адреса — нет утверждения»
   выполняется: адрес — родители.

**Четвёртое значение `Source.type`.** Сегодня их три — `paper | doc | run` (`10` §1,
`07:50`), и `synthesis` их дополняет. Это правка контракта, а не деталь: `/sources` и
`/retrieve` отдают `type` наружу, и потребитель, написавший `if type == "paper" else "run"`,
на четвёртом значении поведёт себя молча-неверно. Объявляется вместе с `Idea.origin` (§5)
одним сообщением соседям.

**Ранжирование — калибровочная ручка, а не готовое место.** Сегодня `score = norm_score +
0.15 · trust_norm` (`retrieve/rank.py:90`), и `trust_score = 0` у гипотезы означает только
отсутствие бонуса. Менторское «сначала трастовые ноды, потом гипотезы» на весе 0.15 не
выполняется: непроверенное встанет вровень с проверенным, если совпало по тексту чуть
лучше. Вес поднимается тогда, когда гипотезы реально появятся в озере, и это подбирается
замером, а не назначается сейчас.

> **[реализация 2026-07-31]** Вес обнулён раньше и по другой причине, чем «гипотез пока
> нет»: `TRUST_WEIGHT = 0.0` в `lake/retrieve/rank.py:29`, обоснование — прямо в коде
> (`rank.py:21-28`): доверие с 2026-07-31 считает LLM-судья (§3.3), число ещё не
> откалибровано, и менять вес одновременно с заменой формулы было бы абляцией, которая
> меняет два фактора сразу и не измеряет ни один. `trust_score` по-прежнему едет в ответе
> `/retrieve` (контракт C3 не тронут) и участвует в формуле `score = norm_score +
> TRUST_WEIGHT * trust_norm` (`rank.py:101`) — член не удалён, а обнулён, и это видно и в
> логе, и в самой формуле, а не только в комментарии. Самопроверка `rank.demo()` отдельно
> проверяет, что механизм жив, а не выпилен: на время одного вызова поднимает
> `TRUST_WEIGHT` до 0.5, убеждается, что доверие двигает счёт идеи, и возвращает вес
> обратно к 0.0 (`rank.py:264-276`, п.4b в коде) — иначе обнулённый вес и вычеркнутая ветка
> неотличимы снаружи, а разница между ними — вся будущая фича.

**Пишет гипотезы блок B, и это отложено** (`12-decisions-meetings.md` §4). Со стороны A
нужно ровно то, что описано выше, и ни строки больше: формат синтетического источника,
снятый инвариант и отсутствие отдельного канала в выдаче.

## 7. Агентский RAG: что нужно от блока A

Агент — часть озера (`12-decisions-meetings.md` §5), ходит на естественном языке, при
нехватке идёт в веб, кладёт найденное через `/fetch`, ждёт переваривания и ретривит снова.
Из этого **уже готово всё**:

| Что нужно агенту | Чем закрыто |
|---|---|
| запрос на человеческом языке | `POST /retrieve`, переписывание в термины решения на 9B (`rewrite.py`) |
| положить найденное в озеро | `POST /fetch` → `202` + задание, очередь переживает рестарт (`queue.py`) |
| дождаться, пока переварится | опрос `GET /ingest/jobs/{id}`: `ok` выставляется **после фазы 2**, то есть когда статья действительно в графе |
| понять, что озеро сломано, а не пусто | `503` против `200 + ideas: []` (`07:126`) |
| контракт интеграции | `GET /openapi.json` открыт без ключа |

**[ревизия 2026-07-31, ревью] Два места, где агент упрётся, и оба видны заранее.**
Пул фазы 1 — **2 потока** по умолчанию (`LAKE_FETCH_WORKERS`, калибровка под общий с
остальной школой пул 9B), очередь — **100 заданий** (`LAKE_QUEUE_MAX`), дальше `429`.
Агент, который в цикле кидает десяток ссылок и ждёт, получит их последовательно, по
минутам на статью; агент, который кидает сотню, получит `429`. Обе ручки — переменные
окружения, крутятся без пересборки, но крутить их надо **до** прогона, а не в момент,
когда эволюция уже идёт.

Решено **не делать** (2026-07-31):

- **не-arXiv ссылки в `/fetch`.** Остаётся `400` до фетча и до трат на LLM; фильтрует агент.
  Цена названа: половина найденного в вебе в озеро не доедет, и это осознанный размен.
- **фильтр выдачи по `source_ids`** («верни идеи из того, что я только что принёс»).
  Свежие тезисы уже в индексе, обычный `/retrieve` их находит.
- **`hops`/глубина обхода параметром C3.** Рёбра пишет B, сегодня их ноль (`07:81`);
  параметр без данных — ручка, которая ничего не делает.

## 9. Что обязано быть правильным

1. **`-1000` не число.** Ни в `run_success`, ни в `effect` листа, ни в том, что уезжает к B.
2. **`dirty` пишется в той же транзакции, что листья.** Иначе флаг врёт при откате.
3. **Усечение видно.** `limit`, отсев по `-1000`, отсев по `min_abs_delta` — все три
   попадают в отчёт числами. Молчаливое усечение читается как полнота.
4. **Отказ судьи не даёт числа.** Не `0.0`, не старое значение молча — `dirty` остаётся,
   отказ попадает в отчёт. Ноль в этом поле означает «оценили и не доверяем» либо «оценивать
   нечего, листьев нет» — но никогда «оценка не удалась».
   `trust_scale()` фиксирована 1.0, второго выражения шкалы в коде нет.
5. **Повторная заливка того же лога ничего не удваивает** — ни листьев, ни источников:
   `text_hash` внутри источника и `UNIQUE(source_id, text_hash)`, в Neo4j — одиночный
   constraint на вычисляемый `leaf_key` (§4.2).
6. **Недоступный Neo4j не превращается в пустое озеро.** Никакого фолбэка на SQLite:
   `503`, а не `200 []`. Несогласованная конфигурация — отказ на старте в обе стороны (§4.1).
7. **Идея без листьев — либо гипотеза (`origin="synthesized"`, `trust_score = 0`), либо
   поломка.** Третьего значения у этого состояния нет (§5).
8. **Строка staging всегда полная.** `draft` и `idea_fields` присутствуют у листа формата
   `run` так же, как у листа из статьи: без них падает отчёт фазы 2 (`run.py:432-433`),
   а не «просто не хватает полей» (§2.2.1).
9. **Утечка конкретики из лога проверяется своим списком.** Зелёная проверка утечки,
   написанная под статьи, на логах не значит ничего (§2.2.1).
10. **Судья видит ограниченный и названный срез листьев.** 16 из N, отбор детерминирован,
    оба числа в трейсе (§3.3).
11. **Заливка логов идёт по своему staging-файлу.** Общий файл сносит корпусный курсор и
    утаскивает в граф источники, ждущие приёмки (§2.3).
12. **Отчёт называет каждый отсев и каждый отказ своим числом**, и в `/stats` они видны
    так же: `run_sources`, `run_theses`, `rows_unparsed`, `dropped_dead` (`-1000`),
    `dropped_no_fitness`, `dropped_root`, `dropped_min_delta`, `limit`, `trust_failed`,
    `trust_leaves_capped`. Одно суммарное «пропущено» склеивает противоположные исходы —
    ту же ошибку уже чинили разведением `theses_skipped` и `theses_refused`
    (`lake/README.md:191-195`).

> **[реализация 2026-07-31]** П.12 обещает эти числа и в `/stats` — `ops.stats()`
> (`lake/ops.py:206-222`) их не отдаёт: там `counts()`, `queue`, `workers`,
> `theses_indexed`, `in_sync`, `ideas_without_leaves`, `trust_scale`, `staging_lines`,
> `staging_cursor`, `pending_link`, `job_running`, и ничего из перечисленного в п.12.
> `run_sources`, `run_theses`, `dropped_dead`, `trust_failed`, `trust_leaves_capped` и

> `False` (тот самый первый абзац §3.2: «сейчас в поле пишется False и его никто не
> двигает»), а не то, что реализовано сейчас: `maybe_rederive` флаг не снимает (см. правку
> в §3.2), и после него `dirty` остаётся поднятым, поэтому проверка красна на верно
> работающем коде. Проверка 6.20 (выгрузка в vault) падает на несовпадении шаблона
> заметки идеи — в фактически сгенерированном тексте есть строки `trust_score: 0.0` и
> `rederived_at_leaf_count: 0`, которых ожидаемый в тесте эталон, судя по расхождению, не
> содержит. Ни одна из этих девяти проверок не редактировалась этой правкой спеки — она
> только фиксирует наблюдаемое поведение на момент чтения; число может устареть раньше,
> чем эта строка будет прочитана снова.

## 12. Чего сознательно нет

- **Рёбер** — целиком у B (§3.1): создание, вес, `evidence`, затухание, типизация,
  гиперрёбра, предложение «связывать идеи из одной ветки эволюции»
  (`12-decisions-meetings.md:123`). Отсюда уезжают только листья и исход мутанта.
- **Формулы доверия** — отменена решением встречи 5 в пользу судьи (§3.3).
- **Синтеза гипотез** — блок B, отложен вместе с бюджетом (`12-decisions-meetings.md` §4).
  Здесь только форма синтетического листа, чтобы, когда он появится, ретрив не переделывать.
- **Домена и тегов** — решение 2026-07-31: не берём. Цена названа: отрицательный результат
  («в этой области приём вредит») остаётся текстом внутри идеи и не фильтруется запросом
  (`12-decisions-meetings.md` §2).
- **Не-arXiv `/fetch`, фильтра по `source_ids`, `hops` в C3** — §7.
- **Боевой заливки логов** — решение «сначала код, потом решим» (2026-07-31). Конвертер и
  судья пишутся и проверяются на фикстурах; заливка трёх CSV — одна команда, когда скажут.
  До неё `effect_observed` остаётся пустым у всех идей, и это надо помнить, глядя на выдачу.

1. **Где живёт база, которую читает B.** Локальный Neo4j у A против Aura у B — §4.4 п.1.
